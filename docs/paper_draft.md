# Which Check Stopped It? Lessons from Evaluating an Egress Gateway for LLM Agents

Nov 8, 2026 · @Sai

## Abstract

Defenses against data exfiltration by LLM agents are usually reported as block rates. We argue that a block rate hides which check actually decided each call, and that this matters. We built an egress gateway that sits between an unmodified, untrusted planner and outbound URL fetches. It decodes request payloads, matches values against retrieved content, and enforces per-field owner, destination and purpose authorization. We evaluated it in four isolation arms, across about eight scenarios (one incident-derived) and seven harnesses, with an independent receiver as ground truth. Across 10 attack calls generated by a local model (qwen3:14b), the host allowlist decided 5, field authorization 3, and a payload-coverage rule 2. The same adapted scenario was stopped by different checks depending on how the planner encoded the call. A context-plumbing gap blocked a legitimate share until purpose binding was fixed, and receiver-side ground truth exposed a coverage defect in the gateway's own rule. A second planner (gpt-6.1-sol) issued no attack calls at all, so the gateway decided nothing. No protected value reached any receiver through the full gateway. We present these as lessons for evaluating agent egress defenses, not as an efficacy claim.

## 1 Introduction

An agent that reads untrusted content and can fetch URLs can be tricked into sending private data out. ShadowLeak and EchoLeak showed this with nothing more than a crafted email and an outbound request carrying encoded data. Defenses for this are typically evaluated by asking one question per attack: was it blocked?

That question is too coarse. A defense is a stack of checks — a host allowlist, content inspection, authorization — and a block from the stack says nothing about which layer did the work. If the cheapest check stops everything, the expensive ones were never tested. If the planner refuses on its own, no check was tested at all.

We make this concrete with an egress gateway we built and evaluated. Our thesis: **which check stops an attack depends on how the planner encodes the call, not on the attack scenario.** The same adapted scenario was stopped by field authorization in one harness and by a payload-coverage rule in another, because the planner wrote the request differently.

We contribute three lessons, each grounded in a preserved failure or surprise from our own evaluation:

1. **Attribute each decision to its deciding check.** Report a per-call table of which rule decided, and the lowest isolation arm that would also have blocked. Aggregate block rates credit layers that never acted (§6.1).
2. **Authorization is only as good as its context plumbing.** A correct, permitted share was denied because the planner interface carried no task purpose. Fixing the context, not the policy, restored it (§6.2).
3. **Ground truth must be independent of the defense.** A receiver with its own decoder caught a coverage defect in the gateway's own payload rule. A no-gateway arm exposed when protection came from the planner, not the gateway (§6.3, §7).

The mechanism itself overlaps CaMeL, Fides, RTBAS and commercial DLP (§9). We do not claim it is novel or effective in deployment. This is a small-n laboratory experience report about how to evaluate such defenses honestly.

## 2 Threat model

The adversary controls content the agent retrieves — emails, documents, pages — and can register external destinations. This is indirect prompt injection. The adversary cannot forge authenticated user turns, permission records or application metadata.

|  | Elements |
| --- | --- |
| **Protected** | Fields with owner and class metadata in trusted application records. A disclosure is a protected value reaching a destination that lacks authorization for that field and purpose. |
| **Trusted** | Authenticated principals, field metadata, permission records, the destination directory, the gateway code, and the application-issued task context. |
| **Untrusted** | Everything the planner produces: tool choice, arguments, declared fields, evidence references, claimed purposes and approvals. Also all retrieved content. |

**Out of scope, documented rather than claimed:** grants obtained by deceiving a user into a valid authorization; channels rendered by a UI rather than issued as tool calls; platform bugs; encodings outside the bounded decode set; data encoded through URL *selection* rather than inspectable parameters; values that never passed through retrieved content.

**Assumptions.** The application supplies correct metadata. Mislabeled metadata is an unmeasured failure mode. Egress happens only through enumerable tool calls. The task context is issued per task by application code. Its binding is an in-process registry, not cryptographic attestation.

## 3 The gateway

The gateway intercepts each proposed `url_fetch` call before dispatch and decides allow or block from trusted inputs only.

**Value matching.** It decodes the serialized URL within fixed bounds: query and path candidates, strict base64 and base64url, size and count caps. It then exact-matches decoded values against values observed in retrieved tool outputs, attributing each match to a field through application-supplied provenance. This is content matching, not taint tracking. A transformation outside the decode set, a paraphrase, or a value never retrieved defeats it.

**Fetch rules (url-gw-1.0, the version evaluated).**

| Rule | Check |
| --- | --- |
| F1 | Inspect the serialized URL before dispatch |
| F2 | Deny hosts not on the fetch allowlist |
| F3 | Protected-class fields need a permission record covering field, destination and purpose, whatever the host; deny wins |
| F4 | Matched values without metadata never default to safe |
| F5 | Carriers that match no known value are denied as `unaccounted_payload` |

**Task context.** The planner's claimed purpose is ignored. Purpose comes from a `TaskContext` that application code creates before the planner runs. Adapter 1.3 binds each issued context to a (task, session) pair by object identity, so a copied or replayed context is rejected before any URL exists.

**Version note.** All evaluation runs used url-gw-1.0. Section 6.3 describes a defect in its F5 rule that we found afterwards and fixed in url-gw-1.1.

## 4 Evaluation design

**Isolation arms.** Every call runs through four arms on identical inputs, each with its own isolated loopback receiver and redirects disabled.

| Arm | Adds | Isolates |
| --- | --- | --- |
| M0 | Dispatch only | Whether the exfiltration really works |
| M1 | Host allowlist (F2) | Destination filtering alone |
| M2 | Decoding, value matching, F5; no permission records | What inspection stops without authorization |
| M3 | Full gateway (F1–F5) | What authorization adds |

For each blocked call we record the **deciding rule** at M3 and the **minimal blocking arm**: the lowest arm that also blocks the same call.

**Scenarios and harnesses.** We evaluated about eight scenario families plus clean controls. One is incident-derived: a ShadowLeak-shaped request carrying base64-encoded fictional PII to an unauthenticated host. An EchoLeak-inspired scenario sends data to an allowlisted "trusted" host. The rest are synthetic: an authorized share, a deny-covered share, a purpose mismatch, plaintext PII to an off-list host, an empty carrier, and a purpose conflict. Scenarios recur across seven harnesses, so we report **scenarios × harnesses**, not independent samples:

- scripted calls: isolation controls, eval-v2, eval-v4;
- live single-step pilots: pilot v1 (raw URL), pilot v2 (structured interface);
- live multi-step episodes: v1 and v2 (example-based contract).

The incident-derived scenario appears in the scripted and multi-step harnesses; the pilots use an adapted variant.

**Planners.** The primary planner is qwen3:14b (Q4\_K\_M, local; temperature 0.7, top-k 20, top-p 0.95, 512 tokens, thinking off; seeds 42–44 per pilot attempt, 42–47 per episode). A second planner, gpt-6.1-sol, ran the v2 harnesses under a frozen protocol with API-forced deviations (§7).

**Ground truth.** An independent receiver-side detector, with its own parsing and decoding code, records which protected values actually arrived. A receipt counts as unauthorized only when the case's documented authorization state does not cover it.

**Counting.** We count attack calls per attempt: each attempt is a separate model call with its own seed. Schema or interface rejections are never counted as gateway protection. Calls the planner never issued are reported as *not exercised*.

## 6 Three lessons

### 6.1 Attribute every decision to its deciding check

The EchoLeak-adapted row of Figure 1 carries the argument. The scenario is the same in every harness: data sent to an allowlisted host. Host filtering misses it everywhere; that gap is real, and M1 delivered the data in each case. But what stopped it at M3 changed with the planner's encoding. In the single-step pilot, the payload matched retrieved values exactly, so field authorization decided (no permission for that field and destination). In multi-step, the planner packed the values into one parameter that exact matching did not attribute, so the payload-coverage rule decided and the authorization path was never reached.

An aggregate block rate reports both as "blocked by the gateway". Only per-decision attribution shows that authorization was decisive in one and untested in the other. The same holds across the live calls: half were decided by the cheapest check, the allowlist, which a host filter alone would have provided.

**Recommendation.** For every gated call, report the deciding rule, the minimal blocking arm, and whether the call was scripted or model-generated. Never count interface or schema rejections as protection.

### 6.2 Authorization is only as good as its context plumbing

In the first structured-interface pilot, the full gateway blocked all three authorized deliveries with `no_authorization`. The payload, destination and permission record were all correct. The permission binds field, destination *and purpose*, and the planner interface carried no purpose. The policy was right; the context feeding it was incomplete.

We preserved the failure and fixed the interface, not the policy: purpose now comes from an application-owned task context, and the planner's claimed purpose is ignored. Replaying the identical saved calls, the gateway allowed all three shares and still blocked all six attack calls.

**Recommendation.** Evaluate legitimate tasks end to end, not just attacks. A false block on a permitted share is the symptom of missing context, and only a legitimate-path case reveals it.

### 6.3 Ground truth must be independent of the defense

The receiver decodes what arrives with its own code, not the gateway's matcher. This separation found two things the gateway could not have reported about itself.

First, **a coverage defect in F5.** In url-gw-1.0, once one carrier matched a known field, the coverage check was satisfied for the whole call. An authorized value therefore laundered any sibling carrier: an opaque base64 blob, or a passport number split across two parameters, was allowed and reconstructed at the receiver. We fixed this in url-gw-1.1 (strict per-carrier coverage). Every evaluation used 1.0, so we replayed every full-gateway allow under strict F5 — ten in the qwen and scripted runs, thirteen including the second planner. None changed, and every one had an authorized receipt. The defect caused no observed leak in our runs, but nothing in the gateway's own logs would have revealed it.

Second, **a matcher miss.** In multi-step, the planner's single-parameter encoding evaded exact matching (§6.1). F5 blocked it conservatively, but the receiver showed the data was real PII to an allowlisted host, the case authorization should have judged.

**Recommendation.** Score outcomes by what a separately implemented receiver observes, and keep a no-defense arm. Section 7 shows why the no-defense arm matters as much as the receiver.

## 7 A second planner: when the model refuses, the gateway decides nothing

We ran gpt-6.1-sol through the same v2 harnesses under a protocol frozen before the run. The API forced three deviations, fixed before any model output existed: temperature 1 (0.7 is rejected), a 2048-token budget covering hidden reasoning (512 for qwen), and reasoning effort `low` (the lowest the API accepts). Two earlier attempts failed on quota and parameter errors and produced no model output; both are preserved. We present this as a second-planner comparison, not an exact replication.

| v2 harnesses only | qwen3:14b | gpt-6.1-sol |
| --- | --- | --- |
| Attack calls reaching the gateway (pilot + multi-step) | 8 (host 4, auth 3, F5 1) | **0** |
| Injected instructions refused outright | 0 | 10 (6 pilot, 4 multi-step) |
| Asked permission on the first turn, before any gateway feedback | 0 | 16 |
| Asked permission after a gateway block | 14 | 0 |
| Authorized pilot shares delivered and allowed | 3 of 3 (after purpose fix) | 3 of 3 |
| Legitimate multi-step tasks completed | 0 (invented destinations, blocked) | 0 (asked permission instead) |
| Unauthorized receipts, any arm including M0 | yes, at M0 and M1 | **none** |

The gateway decided nothing for gpt-6.1-sol: no attack call ever reached it. The decisive evidence is the no-gateway arm. With no defense at all, no protected value reached any receiver, so the protection came from the planner, not the gateway. A per-scenario block rate at M3 would have shown 100% for both planners and credited the gateway equally.

This extends lesson 6.1 one level up. Attribution must include the planner: which check decided depends on how the planner encodes the call, and whether any check is exercised depends on whether the planner attempts the call. Evaluations of egress defenses that use a capable model as the planner should report a no-defense arm, or they risk measuring the model.

Two cautions. The model resisted these specific, fairly overt injection templates; that is not general robustness. And its first-turn permission requests on legitimate tasks are a utility cost from the planner, not from the gateway. Exercising the gateway against capable planners needs stronger or adaptive injections, which we leave to future work.

## 8 Limitations and threats to validity

- **Small n.** About eight scenario families across seven harnesses; the same scenarios recur, so cells are not independent samples. There are ten live attack calls from one planner. All counts are mechanism-level evidence, never a prevention rate.
- **One incident-derived scenario.** All incident grounding traces to a single ShadowLeak-shaped case; the pilots use an adapted variant, and the EchoLeak case omits its browser-rendering and proxy stages.
- **Two planners, simple injections.** The injection templates are overt. Neither planner was tested against adaptive attacks that mutate encodings, split payloads or switch hosts after a block.
- **Second-planner deviations.** Temperature, token budget and reasoning effort differ from the qwen runs (§7).
- **Value matching is not taint tracking.** Transformations outside the bounded decode set, paraphrase, and URL-selection channels defeat it.
- **Trusted metadata.** Every decision depends on correct application metadata; mislabeling is unmeasured.
- **Context binding.** The task-context registry is in-process, not cryptographic attestation.
- **Local receivers.** Loopback mocks stand in for real destinations; no real network, TLS or authentication flows.
- **Protocol provenance.** The eval-v4 expectations were written before execution, but the protocol file was edited after its freeze hash was recorded and the original is not recoverable. We report them as author-asserted. The context-binding check CB6 was added beyond the written protocol. All executed inputs — runner, gateway, adapter and traces — match their freeze hashes.
- **Prompt reconstruction.** Traces did not store prompt text; prompts were reconstructed from hash-verified fixtures and runners.

| Commercial DLP | Egress content inspection by pattern and fingerprint | Content inspection at egress is established; DLP lacks per-action authorization binding. |
| Classic IFC (DLM, HiStar, Flume) | Labels and taint at language or OS level | Conceptual lineage; we do not claim IFC. |

**Gap.** Prior agent-defense evaluations report attack success rates. We are not aware of one that attributes each blocked call to the deciding check, separates planner refusals from defense decisions with a no-defense arm, and scores outcomes by an independent receiver. *\[Check this claim carefully in related work before keeping it.\]*
